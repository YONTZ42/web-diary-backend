# myapp-diary

## 概要

`web-diary-backend` は、アクリルスタンドを Web 上で高品質にシミュレーションし、将来的にはそのまま購入までつなげることを目指したアプリケーションです。  
ユーザーは Gallery に展示スペースを確保し、その中の Exhibit としてアクリルスタンド風の画像を飾れます。Gallery は 12 個の slot を持ち、1 slot に 1 つの Exhibit を配置する設計です。

このアプリは、アクリルスタンド市場の拡大と、推し活需要の増加に合った体験を提供したいという問題意識から始まっています。  
既存のアクリルスタンド系 Web サービスは、注文や入稿には強い一方で、購入前に「どんな見え方になるか」「飾ったあとにどう残せるか」までを一貫して体験できるものは多くありません。  
そこで本アプリでは、画像編集に強くないユーザーでも、高品質なアクリルスタンドをシミュレーションし、そのまま物理提供まで接続できる体験を目指しています。

また、アクリルスタンドの 3D 表現を友達に共有できるようにすることで、ユーザーが生成したアクリルスタンドを単なる商品ではなく、思い出として残せるデジタル展示物にしたいと考えています。

## アプリの目的

このアプリの目的は、単に画像をアップロードしてアクリルスタンドを発注することではありません。  
「高品質なアクリルスタンドを、編集負荷をできるだけ低く作り、Web 上で飾り、共有し、思い出として残し、将来的には購入までつなげる」ことを一連の体験として設計しています。

具体的には、次の 3 点を満たすことを狙っています。

- 高精度な画像処理によって、細かい切り抜き編集をしなくても見栄えのよいアクスタを作れること
- Gallery / Exhibit の構造によって、作ったアクスタを「飾る」「並べる」「残す」体験に変えること
- 共有 URL と 3D 表現によって、友達と見せ合えるデジタルな記念品にすること

## アプリ体験

アプリ体験は、次の流れで設計しています。

1. ユーザーはログイン、または Guest として利用開始する
2. 自分の Gallery を確保する
3. 画像処理を通して Exhibit を作成し、Gallery 内の slot に飾る
4. 公開設定した Gallery を slug 付き URL で友達に共有する
5. 将来的には Stripe 連携で購入ページへ進める

Guest モードでは、LP 表示時に `guest_id` を発行し、以後は `X-Guest-Id` で所有データを識別する運用です。  
この方式により、会員登録前でもすぐ体験を始めやすくしつつ、User と Guest の責務を API 上で明確に分離しています。

## 差別化

他のアクリルスタンド提供サイトとの差別化ポイントは、主に次の通りです。

- 注文フォームより先に、展示体験と完成イメージ確認に重心を置いている
- 高精度な背景除去や切り抜きを前提にし、手動編集の負荷を下げている
- 作ったアクスタを Gallery として公開し、URL 共有できる
- 購入して終わりではなく、3D 表現を通して思い出として残せる

つまり、一般的な「グッズ制作サイト」よりも、制作前のシミュレーション体験と制作後の共有体験に寄せているのが特徴です。

## メリット・デメリット

### メリット

- 画像編集に不慣れでも高品質な見た目を目指しやすい
- Guest でもすぐ試せるため、体験開始のハードルが低い
- Gallery 共有により、推し活文脈のコミュニケーションに乗せやすい
- 将来的にシミュレーションから購入まで 1 本の導線にできる

### デメリット

- 高品質な画像処理には計算コストがかかり、システム構成が複雑になる
- 3D 表現や共有機能まで含めると、単純な注文サイトより実装範囲が広くなる
- 物理商品の最終品質は、印刷・素材・製造工程にも依存するため、Web 上の見え方だけでは完結しない

## アプリ設計

このアプリは、ユースケースから逆算して次の構造で設計しています。

- `Gallery`
  ユーザーごとの展示空間。User は自分の Gallery を持ち、Guest も専用エンドポイントから自分用 Gallery を確保できる
- `Exhibit`
  Gallery 内に飾る個別オブジェクト。1 Gallery あたり 12 slot を持ち、各 slot に 1 Exhibit を置く
- 公開 URL
  `slug` を使って Gallery を閲覧専用で共有する
- 認証モデル
  会員ユーザーは JWT、未登録ユーザーは `X-Guest-Id` で扱い、体験開始の速さとデータ所有の整合性を両立する
- 画像処理
  背景除去や YOLO ベースの切り抜き処理は App Runner 本体から分離し、Lambda コンテナで処理する
- 将来の購入導線
  Stripe を前提に、展示体験のあとに購入へ接続できるよう拡張余地を残している

設計上の意図は、アプリ体験を壊さずに精度の高い画像処理を提供し、その上で共有・展示・購入までを段階的に広げられる形にしておくことです。

## 現在の実装範囲

現状の実装では、展示体験と画像処理、公開共有の基盤を先に整えています。

- User ログインと Guest モードの両方に対応
- Google ログインに対応
- Gallery を公開 URL で友達に共有できる
- slug を使って公開 Viewer にアクセスできる
- 購入ページは未実装だが、Stripe を使った決済導線を追加予定

仕様書ベースでは、このアプリは「写真をミニチュア展示室に展示し、公開 Viewer でも見せられる Web アプリ」という位置づけです。  
フロントは LP、アプリ本体、公開 Viewer を分ける構成を前提にしており、バックエンド側もその運用に合わせて設計しています。

## 技術構成

このリポジトリは、Django API・AWS CDK・Lambda コンテナを分離して構成したプロダクト実装です。  
アプリ本体は Django を App Runner 上で運用し、画像処理のようにレイテンシと計算コストが読みにくい処理は Lambda コンテナへ切り出しています。  
単一リポジトリに集約することで開発速度を確保しつつ、実行基盤は API / 画像処理 / インフラで責務分離しています。

この README で主に説明しているのは、バックエンドとインフラ部分です。  
フロントエンドは別リポジトリで管理しており、こちらから参照できます。

- Frontend Repository
  `https://github.com/YONTZ42/acrylicStandFrontend`
- Frontend Hosting
  Vercel に自動デプロイされる構成

この分割により、フロントエンドは UI 改修の速度を優先し、バックエンド / インフラは API 設計や画像処理、運用設計に集中できるようにしています。

- Web アプリのドメイン設計、画像処理、IaC、監視までを一気通貫で扱っている
- 常時応答させたい API と、重い画像処理を分離してスケール特性を分けている
- Guest / User / 公開 URL 共有のような実サービス寄り要件を、DB 制約と API 設計の両面で整理している
- モノレポ構成により、開発速度を維持しながらインフラ変更も同じ文脈で管理している

## ディレクトリ構成

- `DjangoAPI/`
  Django 4.2 ベースのバックエンド API。認証、アップロード、MiniatureMuseum ドメイン、rembg API、テストを含みます。
- `aws-infra/`
  AWS CDK(TypeScript) によるインフラ定義。S3、CloudFront、ECR、Lambda、App Runner、CloudWatch、Slack 通知までをコード化しています。
- `LambdaContainers/`
  画像処理用の Lambda コンテナ群。背景除去や YOLO ベースの切り抜き処理をコンテナイメージとして管理します。
- `doc/`
  監視設計、環境設計、テスト観点などの設計メモ。
- `python_rembg_demo/`
  rembg のローカル検証用サンプル。
- `.github/workflows/`
  GitHub Actions によるデプロイ・運用ワークフロー。

## 全体アーキテクチャ

- API レイヤー
  Django API を App Runner でコンテナ実行。
- ストレージ / 配信
  メディアは S3 に保存し、CloudFront で配信。
- 重い画像処理
  背景除去や YOLO セグメンテーションは Lambda コンテナへ分散。
- 監視 / 通知
  CloudWatch Dashboard・Alarm・SNS・AWS Chatbot(Slack) を CDK で構築。
- データベース
  PostgreSQL は Neon を利用し、初期コストを抑えながら運用している。

この構成は、単純に EC2 や 1 つの Django プロセスへ寄せるよりも構成要素は増えます。  
その一方で、API の安定運用と画像処理のバースト耐性を分けて最適化できるため、将来的なトラフィック増加に対して説明しやすい構成です。  
DB に Neon を選んでいるのは、PostgreSQL の制約表現力を活かしつつ、個人開発段階のコストを抑えやすいためです。

## ワークフロー

このリポジトリでは、主に次の流れでデプロイします。

1. CDK / CloudFormation 実行デプロイ
`aws-infra/` の CDK から、ECR 以外の実行基盤や監視基盤をデプロイします。構成変更をコードレビュー可能にし、環境差分を抑えるための流れです。

2. ECR イメージ更新から App Runner / Lambda へ反映
アプリや画像処理のコンテナをビルドして ECR に push し、App Runner や Lambda が参照するイメージを更新します。アプリ改修時の反映速度を優先した流れです。

## まとめ

このアプリが目指しているのは、アクリルスタンドを「注文する商品」から、「作って飾って共有し、思い出として残せる体験」へ広げることです。  
高精度な画像処理で制作の負担を下げ、Gallery / Exhibit で展示体験を作り、公開 URL と 3D 表現で共有価値を持たせ、最後に Stripe ベースの購入導線へ接続する。  
そのためのプロダクト設計とシステム設計を、このリポジトリ全体で支えています。
